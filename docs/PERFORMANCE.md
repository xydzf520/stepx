# 性能与响应性验证

## 0.2.177：首页发布构建复测

本轮使用同一个优化构建，分别运行两组独立采样，验证不同窗口尺寸下首页构建耗时及测量稳定性。**这不是旧版与新版的提速对比**，也不代表整个应用或数据库操作都达到相同耗时。

- 环境：Linux x86_64，AMD Ryzen 9 7950X，Rust 1.99.1；本地隔离数据，不读取用户数据库。
- 每组 3 个独立进程，每进程覆盖 30 个场景：2 份数据夹具 × 3 种窗口尺寸 × 5 个布局预设。
- 每场景预热 20 次、计时 80 次；统计中位数和 P95，再取 3 个进程相应指标的中位数。
- 每进程只创建一个应用，等待启动工作完成，检查正常后台线程在采样前后处于等待状态，避免重复启动工作干扰。
- 保留每场景中位数和 P95 都低于 15 ms 的原门槛；同机、同协议对照若同时退化超过 25% 和 250 µs，则失败。

以下为带 120 条附加会话的默认全部模块布局，单位 ms：

| 窗口 | 首组中位数 | 首组 P95 | 复测中位数 | 复测 P95 |
| --- | ---: | ---: | ---: | ---: |
| 1000 × 650 | 1.193 | 1.214 | 1.333 | 1.379 |
| 1440 × 900 | 1.243 | 1.256 | 1.228 | 1.264 |
| 1920 × 1080 | 1.243 | 1.257 | 1.234 | 1.259 |

30 个场景全部通过，首组最大 P95 为 1.282 ms，复测为 1.379 ms。小窗中位数仍有约 11.7% 波动，未将同一程序的采样差异当成优化收益。

此指标仅计首页 View 树构造与销毁，**不含 GPU 绘制、实际 FPS、冷启动或手机网络延迟**。首页动作回归另行执行；UI 单元测试通过也不能代替不同系统上的真实拖动与缩放验收。

复测命令：

```sh
python3 desktop/scripts/check-home-performance.py --self-test
python3 desktop/scripts/check-home-performance.py --output artifacts/home-performance.json
```

后续同机对照可使用 `--baseline`；脚本会核对编译器、构建模式、指标、隔离协议与完整场景矩阵，拒绝不兼容的基线。不要与其他重型编译或测试同时采样。数据库完整快照写入、端到端同步和磁盘占用需要分别测量，不由本项结果推断。

## 0.2.154：存储写入的同数据前后对比

记录测量于 2026-11-06，集成版本 0.2.154 的日志日期为 2026-11-07。Linux / Ryzen 9 7950X / release，2 万条合成记录，双方接收相同连续变更；4 次预热、30 次测量，保持落盘与内容校验要求。

| 持久化操作（中位数） | 旧实现 | 新实现 | 同轮 JSON 基线 |
| --- | ---: | ---: | ---: |
| 热快照改 1,000 条 | 44.054 ms | 8.545 ms | 3.887 ms |
| 热快照改全部 20,000 条 | 77.308 ms | 35.969 ms | 5.408 ms |
| 每次重开连接后改 1,000 条 | 56.474 ms | 46.290 ms | 6.259 ms |

热批量路径明显改善，完整快照仍慢于 JSON，不能称“全面提速”。单条修改的 P95 也并未进一步改善。

另测 1,000 个任务中一份草稿变化，包含 UI 克隆、后台比较和持久提交：1.569 → 0.474 ms；不计原有 700 ms 捕获与 300 ms 合并等待，所以不是用户按键到落盘的总延迟。原始数据、序列化范围和结构变化成本见 [完整报告](storage-batch-performance-0.2.154.md)。

## 这次修复

- 背屏预览的横向布局曾把无限宽度传给点击区域索引，导致主线程卡在 R-tree 插入。现在预览区域有明确尺寸，索引也拒绝非有限坐标。
- 每个 17×23 点阵由一个绘制元素处理，灯珠不再分别创建布局节点和点击区域；整个图案仍可被父级预设卡片选中。
- 背屏默认不生成帧、不扫描图库。进入后启用预览，离开或最小化后暂停，返回时延续进度并保留手动暂停选择。最小化状态检测使用 Linux / Windows 的本地窗口状态；macOS 本轮未实测。
- 图库扫描进入后台线程，只在打开图片页或主动刷新时启动；静态预设缩略图只生成一次。
- 未进入扫码流程时不生成二维码。空闲轮询由每秒 10 次改为每秒 2 次；连接检测保留。进度动画限制为每秒 4 次，倒计时按秒刷新。
- Amoo / Work 的 Markdown 解析按内容缓存，最多 64 条、原文总量 2 MiB，单条超过 256 KiB 不进入缓存。非活动页面不启动额外的附件预览下载。
- 投屏窗口位置查询和停止进程等待移到后台；关闭侧栏只释放该窗口的渲染资源，避免重置其他窗口正在使用的 GPU 实例。
- 同一用户配置只允许一个客户端实例。重复启动通过本机回环连接唤起已有窗口；持有系统文件锁而非用 PID 文件判断存活，崩溃或断电后不会残留占用。唤起监听空闲时阻塞等待，不增加定时轮询。

用户主动开始的传输、生成、应用背屏和任务执行仍会继续接收结果；退出页面不会取消手机上已应用的效果。

## 实际检查

| 检查 | 结果 |
| --- | --- |
| 原先黑屏的背屏页面 | 调试版从启动到截图约 4.5 秒，原故障复现时超过 40 秒仍无响应 |
| 12 个页面连续切换 4 轮 | 48 次通过；包含首页、背屏、Amoo、Work、文件、应用、短信、电话、工具、连接、账号、关于 |

| 非活动背屏 | 断言验证预览停止、时间不再推进 |
| 最小化与恢复 | 原生窗口最小化后预览停止、时间冻结；恢复后继续播放，断言通过 |
| 切页内存观察 | 预热后约 266–269 MiB（调试版），后续轮次未持续增长 |

| 界面单元测试 | 42 项通过，包括非法坐标回归、预览生命周期、缓存上限和已有交互逻辑 |

| 已安装客户端单实例 | 同时再次启动 4 次仅保留原窗口；最小化后再启动，原窗口恢复并获得焦点 |

以上为当前 Linux 机器上的测量，不代表所有电脑上的性能保证。框架独立测试目标存在原有测试依赖/测试 API 缺失，本轮未通过编译；相关非法坐标回归已在桌面客户端测试目标中执行并通过。
