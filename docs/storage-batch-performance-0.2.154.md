# 批量快照与增量写入验收 · 0.2.154

日期：2026-11-06。**1,000 条批量变更的热快照写入从 44.054 ms 降至 8.545 ms，耗时缩短至原来的 1/5.16；仍是同轮 JSON 写入的 2.20 倍。** 此次修复没有将所有完整快照写入变成比 JSON 更快，也没有将存储 API 数字当作页面帧率或整机 CPU 改善。

## 已修改的生产路径

`data_store::write/write_json` 现在复用已验证快照中的行与头字段边界。每个未变值与外部 JSON 框架必须逐字节相同；变化值独立验证，数组稳定 ID 必须不变。保持结构的批量更新只修改对应行的正文、时间和同一事务内的快照头及修订号，不重建所有记录的字符串、身份映射和分页索引。

插入、删除、键或 ID 变化、分区类型变化、需要重新定位的排序变化仍使用完整事务对账。通用路径复用旧行映射完成删除检查，避免复制整份删除集合；对象根快照减少一次重复的完整 JSON 扫描。SQLite 每连接页缓存设置为有界 8 MiB。`WAL + synchronous=FULL`、512 页自动 checkpoint、提交及恢复语义保持不变。

缓存仍检查其他连接的 `data_version`、快照修订和本连接 `total_changes`；提交成功后才发布新缓存。单连接仅保存最近一个快照，跨快照轮换、外部写入、首次写入和结构变化可能走通用路径。此限制不能用热缓存成绩掩盖。

预编译逐行 UPDATE 与单语句 `UPDATE ... FROM json_each` 均做过实验。后者需要额外 JSON 编码和物化，1,000 条/20,000 条变更分别约 11.3/48.9 ms，慢于前者约 9.3/36.8 ms，因此未保留该分支。实验数字受当时其他任务负载影响，不与下表静默窗口的最终测量混用。

## 公平完整快照对照

- 同机 Ryzen 9 7950X（16 核、32 线程），Linux 7.0.0-42，Rust release、`--no-default-features`。旧实现二进制在修改前保留，与新二进制连续运行；没有使用真实用户数据库。
- 数据为 20,000 条确定性合成记录，每条包含 `id/text/at`，快照包含 `device/revision`。紧凑 JSON 为 2,866,717 字节，初始业务库为 6,623,232 字节。
- 每个写入场景预热 4 次，测量 30 次。双方每次接收完全相同的连续值，交错先后顺序。变更构造同样排除，完整序列化和持久提交同样计入。修改数量通过返回的行数断言，结束后双方完整内容逐项相等；这些数字不是“未变化快照跳过写盘”的结果。
- JSON 基线使用原 `local_store::write_if_changed`：读取比较原文件、临时文件写入及 `sync_all`、原子替换、父目录 `sync_all`。SQLite 使用生产 WAL+FULL，测试期间自动 checkpoint 计入写入耗时，没有降低持久化或把 checkpoint 全部移出计时。
- “热快照”保持同一连接和写缓存；“重开连接”每次丢弃连接及应用缓存，计入连接打开、校验和对账。两者均使用热操作系统文件缓存；没有清理系统缓存，因此不称为冷磁盘启动测试。

单位 **ms，中位数 / P95**。JSON 列为新实现同轮、相同值的原文件基线；旧实现同轮 JSON 样本也完整保留在原始文件。

| 场景 | 修改前 SQLite | 修改后 SQLite | 同轮 JSON |
| --- | ---: | ---: | ---: |
| 完整快照仅改 1 条 | 1.579 / 1.776 | 1.612 / 2.213 | 2.734 / 3.302 |
| 完整快照改 1,000 条及头版本 | 44.054 / 49.250 | 8.545 / 9.419 | 3.887 / 4.419 |
| 完整快照改全部 20,000 条及头版本 | 77.308 / 84.407 | 35.969 / 36.991 | 5.408 / 5.814 |
| 每次重开连接后改 1,000 条及头版本 | 56.474 / 59.794 | 46.290 / 54.776 | 6.259 / 7.759 |

批量热快照退化已明显收窄，但仍未消除。单条中位数变化很小、P95 本轮偏高，不能声称单条路径进一步提速。首次或结构变化的完整对账，以及大量散布记录的持久写入仍有成本。以上测量是墙钟耗时，未单独测量 CPU 时间、物理磁盘读写量或 UI 帧率。

原始数据：[storage-0.2.154.json](benchmarks/storage-0.2.154.json)，包含各轮排序后样本、旧/新实现源文件哈希、基准源文件哈希和环境说明。

## 生产增量 API 对照

补测直接调用生产 `apply_delta`，同样为 20,000 条记录中的 1 条或 1,000 条变化，输入、记录位置和头版本变化与完整快照一致。JSON、完整快照、增量三方轮换执行顺序，每方预热 4 次、测量 30 次，结束后核对三份完整内容相等。每方使用独立临时数据库/文件；测量在 UI 测试进程退出后执行。此表是另一次完整三方对照，不把两次测量的 JSON 或完整快照数字交叉计算倍数。

序列化计入三个写入计时。共同的内容变更构造均排除；为增量 API 复制变化 DTO、读取乐观锁头修订的成本分别测量，并给出同一轮逐次相加后的合计。调用方如果必须先读取整份旧快照，该读取与解析成本还应另外计入；本表不能代替该调用方的完整操作耗时。

单位 **ms，中位数 / P95**。

| 相同变更 | JSON 完整替换 | SQLite 完整快照 | `apply_delta` 写入 | DTO 构造 | `read_head` | 增量含构造与读头合计 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 条 | 3.229 / 3.613 | 2.117 / 2.525 | 0.037 / 0.048 | 0.001 / 0.001 | 0.023 / 0.037 | 0.059 / 0.075 |
| 1,000 条及头版本 | 4.265 / 4.892 | 9.174 / 9.527 | 5.764 / 6.341 | 0.586 / 0.618 | 0.024 / 0.050 | 6.371 / 6.926 |

`apply_delta` 保留修订校验和原子提交。对于不要求改变位置的已有行，直接更新正文，避开位置子查询和分页索引维护；只有返回零行时区分“未变化”和“缺失”，缺失记录再追加。单条变化收益明显；1,000 条增量也降低了完整快照的解析及索引维护成本，但 **含前处理后仍慢于同轮 JSON**，不作“增量必然全面更快”的结论。

原始数据：[storage-delta-0.2.154.json](benchmarks/storage-delta-0.2.154.json)。已接入的生产调用方及仍走完整快照的边界见存储接入矩阵；本基准只证明实际生产 API 的性能，不替代 UI、真实手机或端到端用户操作验收。

## 高频 Journal 草稿保存

`amoo_workspace/tasks.json` 的生产写入已从整JSON替换改为 `JournalWriter` 记录级事务。下表测量1000个任务、每任务6轮合成沟通正文（紧凑JSON **2,027,634字节**），每次只修改第500项的一份草稿。30次样本、4次预热、双方接收相同连续值并交错顺序；结束后完整内容相等。用户正常0.2.153客户端仍在后台运行，未为跑分强杀；隔离demo/UI测试进程已结束，无并行编译。

单位 **ms，中位数 / P95**。

| 单草稿变化的实际处理成本 | 旧 Journal JSON | 新 Journal 增量事务 |
| --- | ---: | ---: |
| UI 整 Journal 克隆 | 0.110 / 0.122 | 0.113 / 0.159 |
| 后台比较、序列化/DTO、提交及旧基线释放 | 1.461 / 1.701 | 0.363 / 0.458 |
| 合计 | **1.569 / 1.809** | **0.474 / 0.574** |

同轮合计中位数改善约 **3.31倍**。既有700ms草稿捕获与300ms合并等待均不算入处理时间，用户从按键到持久提交的延迟仍包含这些等待；这不是UI每帧耗时。初始化完整读取与既有规范化为9.033ms，独立报告、不混入热写。worker保留同一修订的类型化已提交基线，每次保存不重新读取整历史或读头；整Journal克隆和O(N)比较仍然存在，单个变化Task内的对话正文也仍随该Task序列化。

JSON基线严格复现原 `Journal::save`：紧凑完整序列化、临时文件权限、文件`sync_all`、原子替换；原实现没有父目录同步。新库仍为生产WAL+FULL，未降低持久化级别以获得收益。原始样本：[storage-journal-0.2.154.json](benchmarks/storage-journal-0.2.154.json)。

Journal的28项模块测试通过，其中新增5项覆盖旧JSON完整迁移且原字节不变、草稿与`Turn.at_ms`只改变目标行、删除/排序/置顶原子提交、陈旧写入拒绝、故障后保持待提交草稿、无需新编辑的后台重试，以及关闭冲突时私有恢复副本。完整接入与恢复边界见[调用方矩阵](storage-consumer-integration-0.2.154.md)。

## 正确性验证

最终 `data_store::` 的 15 项测试全部通过，覆盖迁移与完整回读、Unicode 与转义、多行正文/头字段长度变化、插入/删除/重排/ID 与分区类型变化、缓存跨连接及本连接 SQL 失效、强杀未提交事务、磁盘满、失败后重试、损坏旧文件与未来 schema、含 WAL 的备份以及并发读取。

新增批量故障用例在第 31 条记录触发 SQL 错误，确认之前修改全部回滚，头和行保持原提交值；无效 JSON 尾部不能写入。增量用例以触发器禁止 `position` 更新，确认“保持位置”的正文修改不会维护该列；未变化 DTO 返回 0 且不增加修订。无字符串 ID 的数组条目只允许明确的非负位置及匹配的 `#位置` 标识，缺少位置或 ID 不符会回滚整个事务；陈旧修订仍被拒绝。
