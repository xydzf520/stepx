### 已接入的记录级事务

- `diagnostics::append` 读取旧记录的 ID/时间用于保留策略，**不重新反序列化、序列化旧正文**；只插入本批日志并删除过期/超额 ID。300 条已有日志下新增一条并淘汰一条，SQLite `total_changes` 精确增加 **3**（新增行、删除行、快照 revision）。
- `work_sync` 的排队、单文件送达/失败和重试通过 `save_changes` 只上插变化的投递记录；清理完成历史只删除选中的 ID。20 条队列更新一条投递进度，SQLite `total_changes` 精确增加 **2**（目标行、快照 revision）。幂等去重、待投递上限与暂存保护仍读取受限队列进行业务判断。
- `action_ledger` 的采纳、状态变化、进展备注、撤销、候选同步和来源变化重新核对全部通过 `write_actions` 原子写入**发生变化的行动及标量 revision**；完整账本和来源仍先进行验证。20 条候选中仅一条来源修订变化时，`total_changes` 增加 **3**（目标候选行、逻辑头、存储 revision）；新账本初始化完整写一次。
- `context_ledger` 的常规采集、资料导入/显式整理、关系更正、加载时的旧数据修正及生成失败时保留新证据，全部共用 `persist_ledger`。它比较完整 `Evidence` 值（包括来源、原文和修订历史），只序列化发生变化的证据；证据删除、来源集合、关联、overview 分区和标量头一起提交。128 条证据中修改/新增/删除各一条、增加一个排除会话及更新捕获时间时，`total_changes` 精确增加 **6**；未变化的视图不推进存储 revision。
- `amoo_workspace::Journal` 的 `tasks.json` 已迁入同一业务库。700ms 草稿捕获和300ms后台合并保留；writer以同一修订的类型化基线比较完整 `Task`（包括 `Turn.at_ms`），只序列化变化任务，任务删除/排序、删除会话标记和置顶会话分区同事务提交。24条历史中仅一份草稿/消息时间变化时，`total_changes` 精确增加 **2**（目标任务行、存储revision），其他正文不重写；工作室导入作品也走该writer。
- 公共 `apply_delta` 要求持久化 revision 匹配，删除、行更新和头信息一次提交；ID 不匹配或陈旧写入使整个事务回滚。分页调用方先 `ensure_imported`，避免只查询新库而漏掉旧 JSON。

### 尚未等同于全量改造的部分

上下文和行动的集合写入口现在由调用方提交实际变化行；跨来源排除、关联、期间汇总和引用校验仍读取完整业务视图，不能为了页数或跑分裁剪输入。`context_pipeline` 每个任务是独立快照，保存的是该任务的尝试、成果引用和投递状态；不会为了更新一个任务重写整份任务历史，因此保留任务内的小对象快照入口，底层仍做记录差分。手机会话/通知/相册/目录的协议读取窗口未变成 SQL 分页接口。本文不宣称所有页面已实现端到端数据库分页或整机固定倍数加速。

补漏审计保留以下整对象边界：`material_inbox` 保存至多256项、读取上限2 MiB的来源清单（标题、摘要、状态及原件路径），用户明确收集/处理/忽略时原子保存；原件和解析正文是独立文件。30/60秒后台刷新调用只读 `snapshot`，只有发现上次中断的处理状态时修复一次，不持续重写原文。`studio` 收藏库至多200项/1 MiB，在用户保存或整理时整写；应用商店目录和64组搜索/128项详情缓存按联网查询结果更新；最近文件保存的只是扫描偏好而非扫描出的原文。用量缓存保存会话/消息ID及计数，没有对话原文，仅计数变化时整写。`amoo_sync` 当前仍完整序列化手机快照用于内存签名判重，不是磁盘写入；协议级增量读取和该CPU开销不计入本次SQLite写入加速。任务日志的后台草稿保存另由 `amoo_workspace` 的增量接入覆盖。

### 上下文冷/热写入路径与内存代价

- 新账本、旧 JSON 首次迁移、旧账本缺少现有分区时，完整初始化/升级一次，保留旧 JSON，不把它计作热更新。
- 后续每次业务操作先读取完整 ledger，在本次操作内创建 `LedgerCommitBase`：保存持久化 revision、旧证据的类型化副本和不含证据原文集合的元数据。它不是跨操作/跨账号的长期缓存。计算完成后逐值比较，未变化证据不重新序列化、不进入写入 DTO；全部变化同事务提交，陈旧基线被拒绝。
- 基线带来一份旧 `Evidence` 集合的临时内存副本，加上派生元数据比较所需的 JSON 值；处理结束后释放。它降低序列化和 SQL 写入量，**并未消除完整读、关系计算或 O(N) 比较，也不承诺降低峰值内存**。
- 使用已有保守字节上界检查容量；只有接近 64 MiB 硬上限、上界不能证明安全时，才完整序列化一次计算精确大小，最终仍只提交变化行。容量校验、同一 revision 事务和来源校验没有为性能放宽。

### Journal 迁移、失败与内存边界

- 首次读取旧 `tasks.json` 时验证并迁移，原JSON逐字节保留；旧文件缺少的删除/置顶分区补为空数组。启动时仍完整读取任务、执行既有中断状态修正和草稿去重，SQLite成为后续来源；不双写旧JSON，升级前需结束旧版本写入。
- UI现有整Journal克隆和writer的O(N)类型化比较仍存在，保留一份已提交基线；writer成功后交换所有权，不再额外克隆整历史。草稿变化不再完整JSON序列化；没有把此改动描述为消除整历史读取、比较或降低所有场景峰值内存。
- 发生SQL失败时待提交Journal不变，后台在下一次空闲等待后重试，即使没有新编辑也会重试，并把错误传回页面。陈旧修订不会自动重载后覆盖其他写入；关闭后仍冲突/失败时尝试保存私有 `tasks-unsaved-时间.json`，含基线修订和待提交Journal，供显式恢复，**不自动合并进数据库**。磁盘满等同时阻止数据库和恢复副本落盘时无法承诺强杀后保留尚未提交草稿，但已提交数据不会被清空。
- 加载损坏数据时writer不启动；无基线的默认空Journal和陈旧直接保存均不能覆盖已有记录。草稿、删除/置顶、冲突、失败后无新编辑自动重试和恢复副本均有隔离fixture回归测试。
- 性能对照使用1000任务、每任务6轮合成正文；计入整Journal克隆、比较、DTO和写入，启动完整读取另报。数值及原始样本见批量/增量性能报告的Journal章节。
